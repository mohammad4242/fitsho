# طراحی قابلیت احراز هویت فیتشو

تاریخ: ۱۴۰۵/۰۵/۰۲

## ۱. هدف

اولین قابلیت اجرایی فیتشو، احراز هویت چندکاربره با ایمیل و رمز عبور است. این قابلیت
ستون فقرات مالکیت داده را ایجاد می‌کند تا در مرحله بعد هر پروفایل ورزشی و سلامتی فقط
به صاحب همان حساب متصل شود.

خروجی این مرحله باید یک مسیر کامل از رابط کاربری تا پایگاه داده داشته باشد: کاربر
ثبت‌نام می‌کند، به‌طور خودکار وارد می‌شود، صفحه محافظت‌شده را می‌بیند، خارج می‌شود و
دوباره می‌تواند وارد شود.

## ۲. محدوده

موارد داخل این مرحله:

- ثبت‌نام با ایمیل و رمز عبور
- ورود و خروج
- دریافت اطلاعات عمومی کاربر فعلی
- نشست‌های مستقل برای چند دستگاه
- صفحه‌های ثبت‌نام، ورود و داشبورد محافظت‌شده
- ساختار پایگاه داده و مهاجرت‌ها
- اعتبارسنجی، مدیریت خطا و آزمایش‌های مرتبط
- مستندسازی راه‌اندازی

موارد خارج از این مرحله:

- تأیید ایمیل
- فراموشی یا تغییر رمز عبور
- ورود با شماره تلفن یا سرویس‌های بیرونی
- نقش‌ها و سطح‌های دسترسی
- پروفایل ورزشی و سلامتی
- برنامه تمرینی، تغذیه و هوش مصنوعی
- آزمایش کامل مرورگر
- ریزخدمت، صف کار، حافظه نهان و پردازش پس‌زمینه

قبل از انتشار عمومی روی اینترنت، محدودسازی تعداد تلاش ورود، تنظیم نهایی دامنه و
گواهی امن، و سیاست بازیابی حساب باید در یک مرحله سخت‌سازی جداگانه طراحی شوند. این
سند برای ستون فقرات نسخه اولیه است و ادعای پوشش تمام نیازهای عملیاتی انتشار عمومی
را ندارد.

## ۳. گزینه‌های معماری بررسی‌شده

### ۳.۱. تک‌برنامه ماژولار پایتون و رابط کاربری مستقل

```text
FastAPI modular monolith
React single-page application
PostgreSQL
```

اجزا شامل مرورگر، رابط کاربری مستقل، رابط برنامه‌نویسی ماژولار و یک پایگاه داده
رابطه‌ای است. درخواست از فرم مرورگر به رابط برنامه‌نویسی می‌رسد، در لایه سرویس
اعتبارسنجی و پردازش می‌شود و سپس در پایگاه داده ذخیره می‌شود.

مزایا:

- مرز روشن میان رابط کاربری، منطق برنامه و پایگاه داده
- مناسب برای افزودن برنامه موبایل در آینده
- هماهنگی زبان پایتون با محاسبات و قابلیت‌های هوش مصنوعی آینده
- امکان نگه‌داشتن ماژول‌ها در یک واحد قابل استقرار ساده

معایب:

- احراز هویت و پنل مدیریت آماده در اختیار نمی‌گذارد
- رابط کاربری و بخش سرور دو فرایند ساخت جدا دارند
- تصمیم‌های امنیتی باید صریح و آزمایش شوند

پیچیدگی: متوسط

بهترین کاربرد: محصولی رابط‌برنامه‌نویسی‌محور با چند مصرف‌کننده احتمالی و منطق
پایتونی رو به رشد.

### ۳.۲. تک‌برنامه جنگو با صفحه‌های تولیدشده در سرور

```text
Django
Django Templates
HTMX
PostgreSQL
```

فرم مرورگر مستقیماً به برنامه جنگو ارسال می‌شود. جنگو احراز هویت، نشست، مدل داده و
تولید صفحه را انجام می‌دهد.

مزایا:

- سامانه آماده کاربر، نشست، مجوز و پنل مدیریت
- تعداد کمتر تصمیم‌های زیرساختی در شروع
- سرعت بالاتر برای محصول‌های عمدتاً فرم‌محور

معایب:

- جدایی رابط برنامه‌نویسی و رابط کاربری کمتر آشکار است
- برای برنامه موبایل یا رابط بسیار تعاملی احتمالاً به لایه رابط برنامه‌نویسی جدا
  نیاز پیدا می‌کند

پیچیدگی: کم تا متوسط

بهترین کاربرد: پنل‌های مدیریتی و محصول‌هایی که تحویل سریع صفحه‌های فرم‌محور هدف
اصلی است.

### ۳.۳. برنامه کامل تایپ‌اسکریپت

```text
Next.js
TypeScript
PostgreSQL
```

صفحه‌ها و منطق سمت سرور در یک چارچوب قرار می‌گیرند و هر دو با یک زبان نوشته
می‌شوند.

مزایا:

- یک محیط زبانی برای رابط کاربری و بخش سرور
- امکانات آماده برای تولید صفحه در سرور
- ساختار یکپارچه برای برنامه‌های وب محتوامحور

معایب:

- مرز اجرای مرورگر و سرور می‌تواند برای شروع پیچیده باشد
- منطق پایتونی آینده ممکن است به سرویس جدا نیاز پیدا کند
- خطر مخلوط‌شدن منطق محصول با منطق نمایش بیشتر است

پیچیدگی: متوسط

بهترین کاربرد: تیم تایپ‌اسکریپت‌محور یا محصول دارای نیاز جدی به تولید صفحه در سرور
و بهینه‌سازی موتور جست‌وجو.

## ۴. تصمیم معماری

گزینه نخست انتخاب شد:

```text
FastAPI modular monolith
React single-page application
PostgreSQL
```

این معماری میان سادگی عملیاتی و مرزبندی آموزشی تعادل دارد. بخش سرور یک واحد قابل
استقرار باقی می‌ماند، اما قابلیت‌ها داخل آن ماژول‌های مشخص دارند. در این مرحله هیچ
ریزخدمتی ساخته نمی‌شود.

جریان اصلی:

```text
Browser
  -> React form
  -> POST /api/v1/auth/register
  -> FastAPI validation
  -> authentication service
  -> password hashing and transaction
  -> PostgreSQL
  -> secure session cookie
  -> protected dashboard
```

## ۵. مرز اجزا

ساختار مفهومی بخش سرور:

```text
backend/app/
├── auth/
│   ├── router.py
│   ├── schemas.py
│   ├── service.py
│   ├── models.py
│   └── security.py
├── database/
└── config.py
```

مسئولیت‌ها:

- مسیریاب فقط قراردادهای اچ‌تی‌تی‌پی، کد وضعیت و کوکی را مدیریت می‌کند.
- طرح‌واره‌ها ورودی و خروجی عمومی را اعتبارسنجی می‌کنند.
- سرویس، حالت‌های کاربردی ثبت‌نام، ورود و خروج را اجرا می‌کند.
- مدل‌ها ساختار ذخیره‌سازی کاربر و نشست را تعریف می‌کنند.
- بخش امنیتی فقط هش رمز، ساخت توکن و هش توکن را انجام می‌دهد.
- بخش پایگاه داده اتصال و مرز تراکنش را فراهم می‌کند.

در این مرحله لایه مخزن جدا ساخته نمی‌شود. نشست پایگاه داده مرز کافی ایجاد می‌کند و
افزودن یک واسط دیگر برای دو جدول فقط پیچیدگی ایجاد می‌کند. اگر پرس‌وجوها در آینده
زیاد یا چند منبع ذخیره‌سازی اضافه شد، این تصمیم دوباره بررسی می‌شود.

ساختار مفهومی رابط کاربری:

```text
frontend/src/
├── features/
│   └── auth/
│       ├── api.ts
│       ├── AuthContext.tsx
│       ├── LoginPage.tsx
│       ├── RegisterPage.tsx
│       └── ProtectedRoute.tsx
├── pages/
│   └── DashboardPage.tsx
├── shared/
└── main.tsx
```

## ۶. انتخاب فناوری‌ها و بده‌بستان‌ها

### ۶.۱. چارچوب بخش سرور

```text
FastAPI
```

نیاز: ساخت رابط برنامه‌نویسی، اعتبارسنجی، تزریق وابستگی و مستندات قرارداد.

دلیل انتخاب: از نوع‌های پایتون و طرح‌واره‌های داده برای تولید قرارداد و مستندات
استفاده می‌کند و با مسیر آینده محصول در پایتون هماهنگ است.

جایگزین‌ها:

```text
Django with Django REST Framework
Flask
Litestar
```

بده‌بستان اصلی: آزادی بیشتر آن نسبت به جنگو به معنی تصمیم‌ها و کد بیشتر برای احراز
هویت است. جنگو برای سامانه دارای پنل مدیریت و مجوزهای گسترده بهتر است. فلسک برای
سرویس بسیار کوچک و کنترل کاملاً دستی مناسب‌تر است. گزینه سوم زمانی بهتر است که تیم
تجربه قبلی و دلیل مشخصی برای انتخاب آن داشته باشد.

### ۶.۲. پایگاه داده

```text
PostgreSQL
```

نیاز: نگهداری مطمئن کاربران، نشست‌ها و ارتباطات آینده.

دلیل انتخاب: تراکنش، محدودیت یکتایی، کلید خارجی و مدل‌سازی رابطه‌ای مورد نیاز محصول
را فراهم می‌کند.

جایگزین‌ها:

```text
SQLite
MySQL
```

بده‌بستان اصلی: نسبت به گزینه نخست نصب و نگهداری بیشتری دارد. گزینه نخست برای نمونه
تک‌کاربره یا آزمایش ساده بهتر است. گزینه دوم زمانی مناسب‌تر است که تیم یا زیرساخت
از قبل بر آن بنا شده باشد.

### ۶.۳. نگاشت شیء و رابطه

```text
SQLAlchemy
```

نیاز: تعریف مدل‌ها، پرس‌وجو و مدیریت تراکنش‌ها در پایتون.

دلیل انتخاب: مستقل از چارچوب وب است و کنترل روشنی بر رابطه‌ها و تراکنش‌ها می‌دهد.

جایگزین‌ها:

```text
SQLModel
Django ORM
Raw SQL
```

بده‌بستان اصلی: از گزینه نخست مفصل‌تر است، اما رفتار صریح‌تر و امکانات بالغ‌تری
دارد. گزینه نخست برای عملیات بسیار ساده مناسب‌تر است. گزینه دوم همراه جنگو انتخاب
طبیعی است. دستور مستقیم برای پرس‌وجوهای خاص و حساس به کارایی مفید است، نه برای تمام
برنامه.

اتصال اولیه هم‌زمان نگه داشته می‌شود تا تراکنش‌ها و آموزش ساده‌تر باشند. غیرهم‌زمان
کردن دسترسی پایگاه داده فقط پس از مشاهده نیاز واقعی بررسی می‌شود.

### ۶.۴. مهاجرت پایگاه داده

```text
Alembic
```

نیاز: ثبت نسخه‌دار تغییرات ساختار پایگاه داده.

دلیل انتخاب: ابزار مهاجرت هماهنگ با ابزار نگاشت انتخاب‌شده است.

جایگزین‌ها:

```text
Manual SQL migrations
Flyway
```

بده‌بستان اصلی: فرایند و فایل‌های اضافه دارد، اما تغییرات ساختار را قابل تکرار و
بازبینی می‌کند. گزینه دوم زمانی مفیدتر است که مهاجرت‌ها میان چند زبان یا چند سرویس
مشترک باشند.

### ۶.۵. اعتبارسنجی داده

```text
Pydantic
email-validator
```

نیاز: بررسی ورودی و خروجی، از جمله شکل قابل قبول ایمیل.

دلیل انتخاب: ابزار نخست بخش اصلی قرارداد داده در چارچوب سرور است. ابزار دوم بررسی
ایمیل را بدون عبارت منظم دست‌نویس انجام می‌دهد.

جایگزین‌ها:

```text
dataclasses
Marshmallow
manual validation
```

بده‌بستان اصلی: مدل رابط برنامه‌نویسی از مدل پایگاه داده جدا می‌ماند و مقدار کمی
تعریف تکراری ایجاد می‌کند. این جدایی از خروج ناخواسته فیلدهای حساسی مثل هش رمز
جلوگیری می‌کند.

### ۶.۶. هش رمز عبور

```text
pwdlib
Argon2
```

نیاز: ذخیره‌نکردن رمز خام و بررسی امن رمز هنگام ورود.

دلیل انتخاب: ابزار نخست یک رابط کوچک برای هش و بررسی فراهم می‌کند و الگوریتم دوم
گزینه پیشنهادی آن است.

جایگزین‌ها:

```text
bcrypt
managed identity provider
```

بده‌بستان اصلی: الگوریتم منتخب عمداً پردازنده و حافظه مصرف می‌کند تا حدس‌زدن رمز
پرهزینه شود. گزینه نخست برای سازگاری با سامانه قدیمی مناسب است. ارائه‌دهنده بیرونی
برای تیمی بهتر است که هزینه و وابستگی بیرونی را در برابر کاهش مسئولیت امنیتی
می‌پذیرد.

### ۶.۷. رابط کاربری

```text
React
TypeScript
Vite
React Router
```

نیاز: ساخت فرم‌ها، مسیریابی و صفحه محافظت‌شده.

دلیل انتخاب: اجزای رابط مستقل می‌مانند، نوع‌ها خطاهای قرارداد را زودتر آشکار می‌کنند
و ابزار ساخت، محیط توسعه ساده‌ای فراهم می‌کند.

جایگزین‌ها:

```text
Next.js
Vue
Django Templates
```

بده‌بستان اصلی: برنامه تک‌صفحه‌ای مسیریابی و ارتباط با رابط برنامه‌نویسی را جداگانه
مدیریت می‌کند. گزینه نخست برای تولید صفحه در سرور و بهینه‌سازی موتور جست‌وجو بهتر
است. گزینه دوم وقتی تجربه تیم با آن بیشتر است مناسب‌تر خواهد بود. گزینه سوم برای
رابط کوچک و فرم‌محور ساده‌تر است.

برای درخواست‌ها از قابلیت داخلی مرورگر استفاده می‌شود:

```text
fetch
```

کتابخانه جدا برای درخواست اضافه نمی‌شود، چون این مرحله به پردازش پیچیده، تلاش مجدد
خودکار یا رهگیری مشترک درخواست‌ها نیاز ندارد.

برای وضعیت کاربر از قابلیت داخلی رابط کاربری استفاده می‌شود:

```text
React Context
```

جایگزین‌های بزرگ‌تر فقط هنگام رشد داده‌های مشترک بررسی می‌شوند:

```text
Redux Toolkit
Zustand
TanStack Query
```

### ۶.۸. آزمایش

```text
pytest
HTTPX
Vitest
React Testing Library
```

دو ابزار نخست آزمایش‌های بخش سرور و دو ابزار بعدی رفتار رابط کاربری را پوشش می‌دهند.
آزمایش کامل مرورگر در مرحله پروفایل چندمرحله‌ای ارزش بیشتری دارد و فعلاً اضافه
نمی‌شود.

جایگزین‌ها:

```text
unittest
Jest
Playwright
```

ابزار داخلی پایتون وابستگی خارجی ندارد ولی مدیریت داده آزمایش با ابزار منتخب خواناتر
است. اجراکننده دوم اکوسیستم بزرگی دارد ولی گزینه منتخب با ابزار ساخت رابط کاربری
تنظیم ساده‌تری دارد. ابزار سوم برای مسیر کامل مرورگر مناسب است ولی در این مرحله
هزینه نصب و نگهداری اضافه دارد.

### ۶.۹. پایگاه داده توسعه و آزمایش

```text
Docker Compose
```

نیاز: اجرای قابل تکرار پایگاه داده بدون نصب مستقیم روی سیستم.

فقط پایگاه داده در محفظه اجرا می‌شود. بخش سرور و رابط کاربری برای اشکال‌زدایی ساده
مستقیم اجرا می‌شوند.

جایگزین‌ها:

```text
Local PostgreSQL installation
Testcontainers
```

نصب محلی برای محیط از پیش آماده مناسب است. گزینه دوم برای مجموعه آزمایش بزرگ و
ایزوله مفید است، اما اکنون وابستگی و زمان شروع بیشتری ایجاد می‌کند.

## ۷. مدل داده

جدول کاربران:

```text
users
-----
id: UUID, primary key
email: TEXT, unique, not null
password_hash: TEXT, not null
created_at: timestamp with time zone, not null
updated_at: timestamp with time zone, not null
```

ایمیل پیش از ذخیره از فاصله ابتدا و انتها پاک و به حروف کوچک تبدیل می‌شود. علاوه بر
بررسی سرویس، محدودیت یکتایی پایگاه داده مرجع نهایی جلوگیری از تکرار است. اطلاعات
ورزشی در این جدول قرار نمی‌گیرد و بعداً در جدولی با مالک مشخص ذخیره می‌شود.
زمان‌ها در بخش سرور با ساعت هماهنگ جهانی ساخته و به‌صورت دارای منطقه زمانی ذخیره
می‌شوند.

جدول نشست‌ها:

```text
sessions
--------
id: UUID, primary key
user_id: UUID, foreign key, not null
token_hash: TEXT, unique, not null
expires_at: timestamp with time zone, not null
created_at: timestamp with time zone, not null
```

حذف کاربر نشست‌های او را نیز حذف می‌کند:

```text
ON DELETE CASCADE
```

هر ورود یک نشست جدا برای همان دستگاه ایجاد می‌کند. مدت نشست در نسخه اولیه هفت روز
و ثابت است. تمدید خودکار و گزینه ماندن در حساب در این مرحله وجود ندارد.

توکن با مولد تصادفی امن کتابخانه استاندارد ساخته می‌شود:

```text
secrets.token_urlsafe(32)
```

توکن خام فقط در کوکی مرورگر قرار می‌گیرد. هش آن در پایگاه داده ذخیره می‌شود:

```text
raw token -> browser cookie
raw token -> SHA-256 -> database token_hash
```

## ۸. قرارداد رابط برنامه‌نویسی

ثبت‌نام:

```http
POST /api/v1/auth/register
```

ورودی:

```json
{
  "email": "user@example.com",
  "password": "a-long-password"
}
```

رفتار:

1. بررسی و نرمال‌سازی ایمیل
2. بررسی طول رمز
3. ساخت هش رمز
4. ایجاد کاربر و نشست در یک تراکنش
5. تنظیم کوکی نشست
6. بازگرداندن اطلاعات عمومی کاربر

خروجی موفق:

```text
201 Created
```

ثبت‌نام موفق به‌طور خودکار کاربر را وارد می‌کند. تکرار رمز فقط در رابط کاربری بررسی
می‌شود و به بخش سرور ارسال نمی‌شود.

ورود:

```http
POST /api/v1/auth/login
```

اطلاعات درست، نشست جدید و پاسخ موفق می‌سازند. اطلاعات نادرست همیشه پیام عمومی
برمی‌گردانند تا وجود یا نبود حساب افشا نشود.

```text
200 OK
401 Unauthorized
Invalid email or password
```

خروج:

```http
POST /api/v1/auth/logout
```

نشست جاری حذف، کوکی منقضی و پاسخ بدون بدنه برگردانده می‌شود. تکرار خروج نیز باید
رفتار امن و قابل پیش‌بینی داشته باشد.

```text
204 No Content
```

دریافت کاربر فعلی:

```http
GET /api/v1/auth/me
```

نشست معتبر اطلاعات عمومی کاربر را برمی‌گرداند. نشست مفقود، منقضی یا نامعتبر پاسخ
عدم احراز هویت دریافت می‌کند.

## ۹. جریان‌های اصلی

### ۹.۱. ثبت‌نام

1. رابط کاربری یکسان‌بودن دو رمز را بررسی می‌کند.
2. بخش سرور داده را اعتبارسنجی و ایمیل را نرمال می‌کند.
3. هش رمز ساخته می‌شود.
4. کاربر و نشست در یک تراکنش ایجاد می‌شوند.
5. اگر محدودیت یکتایی نقض شود، کل تراکنش بازگردانده می‌شود.
6. کوکی نشست تنظیم و کاربر به داشبورد منتقل می‌شود.

### ۹.۲. ورود

1. کاربر با ایمیل نرمال‌شده جست‌وجو می‌شود.
2. رمز با هش ذخیره‌شده بررسی می‌شود.
3. در صورت موفقیت نشست جدید ساخته می‌شود.
4. پاسخ ناموفق جزئیات وجود حساب را افشا نمی‌کند.

اگر ایمیل وجود نداشته باشد، بررسی یک هش ساختگی همچنان انجام می‌شود تا تفاوت زمانی
آشکار میان «حساب موجود» و «حساب ناموجود» کاهش پیدا کند.

### ۹.۳. درخواست محافظت‌شده

1. توکن از کوکی خوانده می‌شود.
2. هش توکن ساخته می‌شود.
3. نشست و زمان انقضا بررسی می‌شوند.
4. کاربر مالک نشست در اختیار مسیر محافظت‌شده قرار می‌گیرد.

نشست منقضی هنگام مشاهده حذف و کوکی متناظر منقضی می‌شود.

### ۹.۴. خروج

1. نشست متناظر با توکن جاری حذف می‌شود.
2. کوکی مرورگر منقضی می‌شود.
3. نشست‌های دستگاه‌های دیگر دست‌نخورده می‌مانند.

اگر نشست از قبل وجود نداشته باشد، خروج همچنان پاسخ موفق بدون بدنه می‌دهد.

## ۱۰. امنیت

در محیط اصلی، کوکی این ویژگی‌ها را دارد:

```text
HttpOnly=true
Secure=true
SameSite=Lax
Path=/
```

نام کوکی محیط اصلی:

```text
__Host-fitsho_session
```

برای رعایت قواعد پیشوند بالا، ویژگی دامنه تنظیم نمی‌شود. در محیط توسعه محلی نام
ساده‌تر استفاده می‌شود و ویژگی ارسال امن فقط همان‌جا خاموش است.

درخواست‌های تغییردهنده علاوه بر سیاست کوکی، مبدأ درخواست را با فهرست مجاز مقایسه
می‌کنند. در محیط اصلی، مبدأ مفقود یا غیرمجاز برای این درخواست‌ها پذیرفته نمی‌شود.
محیط اصلی رابط کاربری و رابط برنامه‌نویسی را زیر یک مبدأ ارائه می‌دهد.

قواعد رمز:

- حداقل ۸ و حداکثر ۱۲۸ نویسه
- پذیرش فاصله
- عدم اجبار مصنوعی به نماد، عدد یا حرف بزرگ
- عدم ثبت رمز یا توکن خام در گزارش‌ها

پاسخ کاربر فقط فیلدهای عمومی را دارد و هرگز هش رمز یا توکن نشست را برنمی‌گرداند.

```text
id
email
created_at
```

## ۱۱. رابط کاربری

مسیرها:

```text
/register
/login
/dashboard
```

فرم ثبت‌نام شامل ایمیل، رمز و تکرار رمز است. فرم ورود شامل ایمیل و رمز است. دکمه
ارسال هنگام اجرای درخواست غیرفعال می‌شود.

هنگام شروع برنامه، وضعیت کاربر با این مسیر تعیین می‌شود:

```http
GET /api/v1/auth/me
```

تا پایان درخواست، وضعیت بارگذاری نمایش داده می‌شود تا صفحه اشتباه برای لحظه‌ای ظاهر
نشود. پاسخ عدم احراز هویت کاربر را مهمان می‌کند. نشست منقضی در هر درخواست نیز وضعیت
کاربر را پاک و او را به صفحه ورود هدایت می‌کند.

تمام صفحه‌ها راست‌به‌چپ هستند. ورودی ایمیل جهت چپ‌به‌راست دارد. خطای هر فیلد کنار
همان فیلد و خطای کلی در ناحیه قابل اعلام برای صفحه‌خوان نمایش داده می‌شود.

درخواست‌های مرورگر کوکی را همراه خود می‌فرستند:

```javascript
credentials: "include"
```

## ۱۲. مدیریت خطا

نگاشت خطاها:

```text
invalid request data -> 422 Unprocessable Entity
duplicate email -> 409 Conflict
invalid credentials -> 401 Unauthorized
missing or expired session -> 401 Unauthorized
database unavailable -> 503 Service Unavailable
unexpected failure -> 500 Internal Server Error
```

جزئیات داخلی خطا فقط در گزارش امن سرور ثبت می‌شوند. رمز، توکن خام و داده حساس در
گزارش قرار نمی‌گیرند.

ایجاد کاربر و نشست یک تراکنش واحد است. شکست هر قسمت نباید کاربر یا نشست نیمه‌کاره
باقی بگذارد.

## ۱۳. راهبرد آزمایش

آزمایش‌های بخش سرور روی پایگاه داده واقعی و مخصوص آزمایش اجرا می‌شوند. استفاده از
پایگاه داده سبک کنار گذاشته می‌شود تا محدودیت‌ها، نوع شناسه و مهاجرت دقیقاً مشابه
محیط اصلی باشند.

موارد بخش سرور:

- اجرای مهاجرت روی پایگاه داده خالی
- ثبت‌نام موفق و تنظیم کوکی
- ذخیره‌شدن هش و ذخیره‌نشدن رمز خام
- جلوگیری از ایمیل تکراری
- رد ایمیل و رمز نامعتبر
- ورود موفق و ناموفق
- دریافت کاربر با نشست معتبر
- رد نشست مفقود، منقضی و جعلی
- خروج و نامعتبرشدن نشست جاری
- بازگشت تراکنش در شکست ثبت‌نام
- بررسی ویژگی‌های کوکی
- رد مبدأ غیرمجاز

موارد رابط کاربری:

- نمایش و اعتبارسنجی فرم‌ها
- جلوگیری از ارسال دو رمز متفاوت
- نمایش خطای رابط برنامه‌نویسی
- انتقال پس از ثبت‌نام یا ورود موفق
- جلوگیری از نمایش داشبورد برای مهمان
- خروج و انتقال به صفحه ورود

آزمایش کامل مرورگر در این مرحله اضافه نمی‌شود. معیار این تصمیم دوباره هنگام طراحی
فرم چندمرحله‌ای پروفایل بررسی خواهد شد.

## ۱۴. معیار پذیرش

قابلیت زمانی کامل است که:

- مهاجرت‌ها روی پایگاه داده خالی اجرا شوند.
- ثبت‌نام، ورود، دریافت کاربر و خروج از رابط کاربری قابل انجام باشند.
- ثبت‌نام موفق کاربر را خودکار وارد کند.
- داشبورد بدون نشست معتبر دیده نشود.
- رمز و توکن خام در پایگاه داده، پاسخ یا گزارش ذخیره نشوند.
- نشست منقضی و جعلی پذیرفته نشود.
- خطاها قرارداد ثابت و بدون افشای جزئیات داخلی داشته باشند.
- تمام آزمایش‌های بخش سرور و رابط کاربری واقعاً اجرا و موفق شوند.
- بررسی قالب و نوع‌های کد موفق باشد.
- راه‌اندازی در فایل راهنمای پروژه مستند شود.
- قابلیت‌های خارج از محدوده وارد این مرحله نشوند.
